# TextileHR AI v4.9.64 — JD coverage and evidence-integrity engineering release

**Prepared:** 13 November 2026. **Build:** `phase7g-v4-9-64-source-coverage-decision-safety-2026-11-13` **Protocol:** `segment_ids_semantic_llm` **v50**. **Previous:** v4.9.63 / v49 (ZIP SHA-256 `c0d7f3a44f3b727ee2c5a744bd4fd5dba0cf7d3250d8335889f48d33b794b2d7`).

## What changed in actual source

1. **Original-JD coverage:** new `cv_ranker/jd_coverage.py` generates exact original structural JD clause mappings to approved `R###`, original line numbers, priority and `covered` / `multiple_possible_mappings` / `unmapped_review_required` dispositions. `CVRanker.prepare_jd_review()` records them with the frozen JD diagnostics. `approve_jd_rows()` recomputes this map **after** reviewer edits. The review screen shows uncovered/multiply mapped source lines. These are **review signals**; the code neither invents extra criteria nor automatically marks a candidate deficient. Known limitation: coverage currently covers *structurally explicit* clauses, not independently gold-labeled complete narrative JD semantics.
2. **Typed evidence modality:** `RequirementConstraint` distinguishes `knowledge_claim`, `performed_work`, `dated_professional_tenure`, `completed_qualification`, `credential_claim`, `eligibility_condition`, and `employer_review_required` from coarse JD `kind`. It separately records whether a numeric time statement is candidate tenure, a non-tenure timeframe pending review, or no duration. The model receives the appropriate existing source-defined field when supplied; scorer weighting policy is unchanged. Historical manually created constraints with missing modality remain compatible.
3. **Corrective JD extraction:** `_sanitize_requirements()` retains specific source-grounding rejection diagnostics even when the caller does not request a diagnostics list. A corrective request receives the actual machine-readable rejection reason. Empty initial model output gets a **distinct source-coverage correction objective** instead of an identical prompt repetition. Legitimate structural fallback remains visible, never called model-validated.
4. **Typed unresolved technical diagnostics:** `cv_ranker/failure_diagnostics.py` creates safe code/next-action summaries for unresolved `R###` with only original source *IDs*, not raw CV/source text or credentials. `UnifiedMetrics.public()` exposes `unresolved_diagnostics` in the existing execution details and preserved per-candidate technical metrics. This is not a full durable retry state machine; score and technical Unverified semantics are unchanged.
5. **Gross unrelated-work false-Found backstop:** `cv_ranker/source_subject_guard.py` denies **automatic direct credit** for a source-valid but totally unrelated *performed-work* claim with **zero substantive common JD subject anchors**. In that case, original evidence requires further review/correction. This is a necessary negative guard, not a synonym scorer. An approved named-condition match with performed work keeps the earlier v48 safe path. The guard is active only for freshly typed work/review standards; old direct manually constructed legacy inputs do not unexpectedly gain new paid retries. Completed semantic equivalences with no common words can require review rather than automatically receiving credit; human review and richer source relations remain needed.
6. **Inflected multi-action work:** A reviewed descriptive `all_of` JD such as “Investigate flaky CI tests and document root causes” can retain model-proposed Found when source shows “Investigated flaky CI tests and documented root causes”; both mandatory work arms must have source anchors and an affirmative completed action. Standalone named-skill AND clauses remain strict; original experience/degree and OR guards are preserved.
7. **Prompt independence:** the focused final judge no longer instructs preservation of an earlier favorable verdict. Its source and omission protections from v49 remain in place.
8. **Real supervisor-branch testing:** `evaluation/evaluate_supervisor.py` keeps the **seven original** controlled cases and now offers `--cross-domain` to execute **15 additional** positive/adversarial cases across QA, finance, HR, logistics, healthcare, networks, maintenance and education/credentials. The intentionally incorrect fake model sometimes proposes Found on unrelated work; validators and final projections must block it. Single-criterion test category weights are assigned to the criterion's actual JD/experience/education scoring category (fixing a previous evaluation-only test issue). The simulated source outputs are *not* independent human labels or live-model precision.
9. **Regression tests:** `tests/test_v4964_coverage_semantics_diagnostics.py` covers exact source coverage, approval recomputation, typed modality and temporal subject, error-code availability, corrected model prompts, 15-case supervisor-path assessment, unrelated action false positives, inflected multi-part valid work and intercepted 301/302/303/307/308 requests with dummy credentials.

## Observed controlled outcomes

- **Original v49 seven-case unified smoke**: 7/7 expected (controlled provider, not real AI).
- **New fifteen-case cross-domain unified smoke**: 15/15 expected under controlled provider, including negative cases where the stub itself wrongly asserts Found. These are **engineering controls**, not general accuracy estimates.
- Existing v48 named three-way alternatives, negative acronym collisions, original source qualifications and v49 frozen dates remain separately tested.
- An earlier attempt at a strict gross-mismatch check regressed legacy manually constructed work requirements. The check was narrowed to **newly source-typed work standards** and the legacy tests were rerun to preserve compatibility.
- The full dependency-incomplete Linux/Python 3.13 container reports **1,406 pass, 22 failure, 10 collection errors** in the last pre-version rerun. The failures were confined to unavailable Streamlit/LangChain/provider environment paths; all identified assessment-semantic regressions were repaired. These are not a green full suite. The exact final source ZIP must be checked separately after packaging.

## Release and migration

- Source validation and JD meaning metadata changed; **v50 must not silently resume or relabel old v49/v48 decisions**. Keep their reports historical; re-upload original frozen JD/CVs for re-assessment under v50. Weight-only changes continue to make zero model calls.
- `CVR_STRICT_SOURCE_HASHES=1 python -m cv_ranker.runtime_check` and packaged ZIP source hashes verify code identity; they do not establish AI quality or remote authentication security.
- No real applicant records, environment secrets, local vector caches or private signing keys belong in the release.
- The application remains a **human-supervised, local decision-support tool**, not credential verification or autonomous hiring.
